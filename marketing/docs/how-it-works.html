How It Works

The full stack, from file watcher to remote peer.

Architecture overview

CrabTalk has three layers. Each one has a single, narrow job.

  ┌─────────────────────────────────────────────┐
  │           crabtalk-daemon  (Rust)           │
  │                                             │
  │  file watcher → manifest diff → libp2p     │
  │                                     QUIC   │
  └──────────────────────┬──────────────────────┘
                         │ named pipe / unix socket (IPC)
  ┌──────────────────────┴──────────────────────┐
  │           MCP server  (Node.js)             │
  │  Claude Code ←→ tool calls ←→ daemon IPC   │
  └──────────────────────┬──────────────────────┘
                         │ REST  (address lookup only)
  ┌──────────────────────┴──────────────────────┐
  │     claw.crabtalk.dev  (Cloudflare Workers) │
  │  POST /api/rendezvous  — register address   │
  │  GET  /api/rendezvous  — fetch peer addrs   │
  │  DELETE               — deregister          │
  └─────────────────────────────────────────────┘
Rust

crabtalk-daemon

Watches ~/.claude/, manages libp2p connections, handles file transfer. Runs in the background.

Node.js

MCP server

Exposes Claude Code tools (sync-now, get-status, etc.) by proxying commands over IPC to the daemon.

Cloudflare

Rendezvous server

A phone book. Stores each device's libp2p multiaddrs so peers can dial each other. Holds no file content.

The daemon

crabtalk-daemon is a small Rust binary that starts in the background when Claude Code launches the plugin. It opens a libp2p swarm on a random port using QUIC transport and listens for connections from other CrabTalk instances.

The daemon exposes a local IPC channel — a named pipe on Windows (\\.\pipe\crabtalk-daemon) and a Unix socket on macOS/Linux (~/.claude/crabtalk.sock). The MCP server connects to this pipe and speaks NDJSON: one JSON object per line, each tagged with a requestId for correlation.

Peer discovery

CrabTalk finds peers two ways, and uses whichever works:

  • mDNS (LAN) — on the same local network, peers announce themselves via multicast DNS and connect directly without touching the rendezvous server.
  • Rendezvous (WAN) — the daemon registers its current multiaddrs with claw.crabtalk.dev every five minutes. When another device looks up your account, it gets those addresses and dials directly.

After the initial address exchange, all traffic is peer-to-peer. The rendezvous server is never in the data path.

File sync protocol

Sync runs in two passes over a libp2p request-response stream:

  1. Manifest exchange — each peer sends a JSON manifest listing every watched file with its path and SHA-256 hash. The initiating peer diffs the two manifests to produce a list of files it needs.
  2. File transfer — for each missing or outdated file, the peer opens a new stream and requests the file by path. The response streams the raw bytes directly; there's no message-size limit because libp2p streams are framed at the transport layer, not the application layer.

All streams are encrypted end-to-end with the Noise protocol and authenticated against each peer's libp2p keypair. A peer that isn't in your account can't read your files, even on the same network.

Conflict resolution

CrabTalk uses last-write-wins by default: the file with the newer modification time wins. If both copies were modified within the same second while offline, it's treated as a conflict — both versions are preserved locally and flagged in the daemon state.

Conflicts surface in Claude Code via the list-conflicts tool and can be resolved with resolve-conflict, which accepts "local" or "remote" as the winning side.

Privacy

The rendezvous server stores only your device name, account ID, and libp2p multiaddrs (IP addresses + port numbers). It never sees file names or file contents. Addresses are purged automatically after 10 minutes of inactivity. File data travels exclusively between your own machines.

Open source

The full source — daemon, MCP server, and rendezvous server — is on GitHub. You can audit it, self-host the rendezvous server, and point the daemon at your own endpoint via the config file.
